# Composition Contract — `renderAnalysisForStudent` + Phase 4 `compositionLayer`

> **Status**: spec for Phase 2 → Phase 4 merger. `renderAnalysisForStudent.ts` is the prototype Phase 4 builds on. This doc fixes the boundary so Phase 4 doesn't accidentally fork.
>
> **Belongs to**: Workstream 04. Phase 2 deliverable (wire) + Phase 4 deliverable (merge).
>
> **Reads**: `FIELD_DISPOSITION_TABLE.md` (which fields go DET vs LENS vs RESIDUE).

---

## Goal

After Phase 7 retires `holisticSynthesis.ts`, the pipeline must still produce the same StudentAnalysisDocument shape from a profile that lacks the L3.75-generated fields. Two render paths can't fork — `renderAnalysisForStudent` already exists as the prototype; Phase 4's `compositionLayer.ts` is the deterministic composition pass that fills in the fields L3.75 used to populate. They share one output type and one section boundary set.

## Boundary

```
EssayProfile
   │  (deterministic composition — no LLM, no judgment)
   ▼
compositionLayer.ts            ← Phase 4 build
   │  (writes back to profile or to a transient ProfileView)
   ▼
EssayProfile + composed fields
   │  (deterministic projection — no LLM, no judgment)
   ▼
renderAnalysisForStudent.ts    ← shipped prototype
   │
   ▼
StudentAnalysisDocument
   │  (deterministic markdown projection — no LLM)
   ▼
renderStudentDocumentMarkdown  ← Phase 2 helper
```

Two layers, one direction. Each layer is pure (no LLM, no IO). The composition layer can be invoked before render or skipped entirely if the profile already has the fields populated.

## Input

`EssayProfile` (from `profileTypes.ts`). The renderer reads these load-bearing slots:

| Profile field | Used by section |
|---|---|
| `aoFirstRead.committeeOneLiner` | §1 Committee one-liner |
| `aoFirstRead.gutReaction`, `putDownRisk`, `hookMoment` | §2 AO reaction |
| `admissionsPositioning.archetypeContext.{archetype, poolDensity}` | §2 AO reaction |
| `findings[].{claim, scope, evidence, coachingValue, status}` | §3 Annotated essay (fallback) |
| `craftAssessment.strengthSignatures[].{quality, evidence, paragraphs}` | §3 Annotated essay (strengths), §6 strengths fallback |
| `scoreMatrix.coachingMap.priorities[].{action, architecturalReason, paragraphs, expectedImpact}` | §4 Revision priorities (primary) |
| `findings[]` (sorted) | §4 Revision priorities (fallback) |
| `northStar.structuralRolesMap[].{role, paragraphs, weight}` | §5 Structural map |
| `paragraphs[].analysis.paragraphVerdict` + `understanding.role` | §5 Structural map |
| `index.improvementPhase.{level, reasoning}` | §6 Overall assessment |
| `scoreMatrix.coachingMap.protectedStrengths[]` | §6 strengths |
| `thematicArchitecture.centralThesis` | §6 central idea |
| `northStar.distinctivenessSignature.articulation` | §6 distinctiveness |
| `admissionsPositioning.archetypeContext.differentiator` | §6 distinctiveness (fallback) |
| `characterRevelation.writerPortrait` | §6 writer portrait |

Anything outside this set is invisible to the student render. New profile fields added in later phases (e.g., L3.5 `contradictionFlags` from Phase 5) extend this list — every extension lands in this doc.

## Output

`StudentAnalysisDocument` (from `presentation/types.ts`). Six sections + meta. The shape is closed — Phase 4 cannot add top-level sections without bumping a schema version on the doc; new content lands inside an existing section's nested type. This keeps the parity-gate diff readable across regens.

The structured JSON is canonical. `renderStudentDocumentMarkdown` is a one-way projection: changes to the markdown shape never change the JSON shape.

## Ownership at the field level

Three states per profile field:

- **DET** (deterministic) — composed by `compositionLayer.ts` from other profile fields via a pure function (e.g., `committeeOneLiner` derived from archetype + writerPortrait). No LLM needed; survives L3.75 retirement.
- **LENS** — generated by a targeted lens prompt (Phase 5) — Voice / Story / Meaning / Admissions. Each lens reads a slice of the profile and writes one field. Survives because each lens is small and cacheable.
- **RESIDUE** — generated by the residue call (Phase 5) — the 4 fields that don't fit any lens (`writerPortrait`, `entanglements`, `arcTrajectory`, `mechanisms`). One Sonnet call, low cost.

The DET / LENS / RESIDUE classification is at `FIELD_DISPOSITION_TABLE.md`. Phase 4's parity gate is the mechanism for *moving* a field between buckets — if a DET formula produces worse output than L3.75 did, the field gets reclassified to LENS/RESIDUE and a prompt is written in Phase 5.

## L5 surfacing — open design call

The L5 ranker (`deepAnnotationService.ts:rankAndSurfaceAnnotations`) sets `surfaced=true` on 20-30 annotations. The renderer today reads from `profile.findings` and `profile.craftAssessment.strengthSignatures`, NOT from the L5 result — because L5 is transient and not persisted on the profile.

**Decision deferred**: either

1. **Persist L5 on the profile** (`profile.feedbackSurface: L5AnnotationResult | null`) and have the renderer prefer surfaced L5 annotations over the finding-based fallback when present. Simplest; one extra field.
2. **Pass L5 as a render parameter** (`renderAnalysisForStudent(profile, options, l5Result?)`). Keeps the profile pure; complicates every caller.

Recommendation: option 1. The L5 result is < 50 KB even for dense essays and is already shaped for downstream consumption. Phase 2 wire writes the renderer's snapshot from profile-only data (today's behavior); Phase 4 or earlier flips the renderer to consume L5 surfaced if present.

## Snapshot artifacts (Phase 2 → Phase 4 bridge)

Every dump regen writes three new files alongside the analytical dump:

| File | What it is | Consumed by |
|---|---|---|
| `<essay>.json` | Full EssayProfile JSON (already shipped under R6) | Phase 4 parity gate input |
| `<essay>-student.json` | StudentAnalysisDocument (Phase 2 wire) | Phase 4 parity gate baseline |
| `<essay>-student.md` | Markdown projection of the above | Manual review during regens |

Phase 4 parity gate: re-run `compositionLayer + renderAnalysisForStudent` against the persisted `<essay>.json` and diff the resulting student doc against `<essay>-student.json`. Worse-than-baseline fields get reclassified DET → LENS/RESIDUE.

## What this contract forbids

- **Two render paths in production.** Anyone tempted to build a parallel renderer reads this doc first; if there's a real gap, it lands as an option on the StudentAnalysisDocument or as an extension inside an existing section's type.
- **LLM calls inside `compositionLayer.ts` or `renderAnalysisForStudent.ts`.** Both are pure transformations. Anything needing a model call belongs in Phase 5 lenses or residue.
- **Markdown projection determining JSON shape.** The JSON is canonical; the markdown follows. If the markdown wants a field the JSON doesn't have, the JSON gets the field first.
- **Implicit field defaulting at render time.** Missing data renders as an explicit blank (`"Distinctiveness analysis pending"`), never a hallucinated stand-in.

## Validation path

- **TSC clean** on every change.
- **Phase 4 parity gate** — run the renderer on persisted Crochet + Three Days JSON dumps; diff against the shipped `*-student.json` baselines. Any worse-than-baseline field is reclassified.
- **Phase 6 verification regen** — single bundled regen exercises the wire end-to-end. The shipped `*-student.md` becomes the audit substrate.
