# Progressive Feedback — Design Note

**Premise:** the prior three audits established that the system produces $500/hr-grade analytical content buried inside a 30,000-word artifact a 17-year-old will not read. The compression problem is severe but it is *also* the wrong frame. The deeper question is:

> **What if every revision doesn't need a fresh full audit?**

A real counselor doesn't re-audit your essay from scratch every time you send a new draft. They remember what they told you last time, check whether you addressed it, surface one or two new things, and pace the rest across sessions. That is what we should build. Compression is a downstream effect of building it right, not the upstream goal.

This document proposes the architecture and walks through the cost / quality / dose trajectory.

---

## 1. The reframe — quality through scarcity, not abundance

The current model: every revision = full pipeline (L1 → L4) = 200+ observations regenerated = $1.40+ = 30,000-word dump.

This model has three problems beyond the rendering issue:

1. **It re-pays for the same insights every revision.** The "milk frame is the thesis" observation is generated by L3 / L3.75 / Findings / Subtext / Pivot Points / Connections / Entanglements every time the student re-runs. They paid $0.20 for that observation in round 1; round 2 charges them another $0.20 for the same observation against an essay that hasn't changed in the relevant region.
2. **It surfaces unranked output.** When the system generates 200 observations, it has no operational definition of "the top 3." The student is asked to triage their own feedback.
3. **It overwhelms the student into inaction.** A student handed 13 `[significant]` concerns will fix zero. A student handed 1 will fix 1. **More feedback produces less action.**

The product the system should deliver is not a comprehensive analytical artifact. It is a **paced coaching relationship across N revisions**. The artifact at any given moment is small. The intelligence behind it is large and persistent.

**Quality through scarcity** means: surface the smallest number of asks that move the essay forward at this revision. Save the rest. Bring them back when they're relevant, in priority order, only after the current asks are addressed.

## 3. The proposed architecture: four layers

```
┌──────────────────────────────────────────────────┐
│ LAYER 4 — Conversation                           │
│ Student asks "what about X?" → pull from below   │
│ Pull-mode, not push-mode                         │
└──────────────────────────────────────────────────┘
              ▲
              │ ad-hoc queries
              │
┌──────────────────────────────────────────────────┐
│ LAYER 3 — Surface (the deliverable)              │
│ ≤ 5 items, ranked, one voice, ≤ 1,200 words      │
│ Phase-filtered, diff-aware                       │
└──────────────────────────────────────────────────┘
              ▲
              │ priority filter + dose cap + voice
              │
┌──────────────────────────────────────────────────┐
│ LAYER 2 — Inventory (the ledger)                 │
│ All findings ever generated, with status:        │
│ surfaced / actioned / carry-forward /            │
│ superseded / retired / never-shown               │
│ Persisted across revisions                       │
└──────────────────────────────────────────────────┘
              ▲
              │ emission + maturity refresh + diff
              │
┌──────────────────────────────────────────────────┐
│ LAYER 1 — Substrate (always comprehensive)       │
│ L1 → L3.75 understanding always full             │
│ L3.5 analysis + L4 crystallization full          │
│ This is the analytical engine. Don't skimp here. │
└──────────────────────────────────────────────────┘
```

### Layer 1 — Substrate (no change in depth, change in trigger)

**Principle: never trade analytical depth for cost savings on the understanding side.** When a student writes a paragraph, we want to deeply understand it. The savings come from not re-doing the understanding when the paragraph hasn't changed.

- First revision: full L1 → L4 pipeline, no shortcuts.
- Subsequent revisions: `selectAnalysisMode()` chooses Comprehensive vs Focused.
  - **Comprehensive** triggers: structural change (paragraph added / deleted / reordered), >40% of words changed, time-since-last-comprehensive > N rounds, student explicit ask.
  - **Focused** otherwise: re-walk only changed paragraphs, re-run L3.5 only for affected regions, re-run L4 against updated finding set.
- The substrate **persists in the profile**, not the dump. Chat (Layer 4) reads from it directly.

**Cost impact:** Round 1 ~$1.40, Round 2-5 ~$0.05–0.20 (Focused mode). This is the existing `selectAnalysisMode()` design — implement and verify.

### Layer 2 — Inventory (the persistent ledger)

**This is the architectural unlock.** Today's `FindingStore` is per-essay-state, not per-coaching-relationship. Extending it:

```typescript
interface InventoryItem {
  id: FindingID;
  observation: string;          // the actual content (one-voice already)
  location: ParagraphRef;       // which paragraph(s)
  kind: 'cut' | 'add' | 'restructure' | 'name' | 'connect' | 'tighten';
  impact: 1 | 2 | 3 | 4 | 5;    // how much it would change the essay if acted on
  effort: 1 | 2 | 3 | 4 | 5;    // how much work for the student
  phase: ImprovementPhase;      // Foundation / Architecture / Craft / Polish / Distinction
  
  // lifecycle
  status: 'never_shown' | 'surfaced' | 'actioned' | 'carry_forward' | 'superseded' | 'retired';
  surfacedRound: number[];      // which revision rounds this was shown
  actionedRound: number | null; // which round the student fixed it
  ignoreCount: number;          // how many times surfaced and ignored
  
  // anchoring
  textFingerprint: string;      // the actual text the observation was about
  contextHash: string;          // the surrounding state when generated
}
```

**Lifecycle rules:**

- `never_shown` → `surfaced` when picked by Layer 3 ranker.
- `surfaced` → `actioned` when next revision's diff shows the targeted region changed AND the issue is no longer detectable.
- `surfaced` → `carry_forward` when the targeted region didn't change (or changed but issue persists).
- Anything → `superseded` when a newer finding subsumes it (e.g., F1 about misdirection becomes superseded by a finer F1' once L3.75 deepens).
- Anything → `retired` when the targeted region was deleted entirely or the essay's structure changed enough that the item no longer applies.
- `surfaced` items with `ignoreCount >= 2` get dampened (drop priority by 1) — the student has signaled they don't want to act on this.

**Re-ranking on each revision:** every inventory item is re-scored against the *current* essay state. An old `carry_forward` item might become #1 in round 3 if the student fixed everything else. Items aren't sticky to their original priority.

### Layer 3 — Surface (the deliverable)

**The student never sees Layer 1 or Layer 2 directly.** They see exactly the Surface render.

**Surface contract:**

- **Hard word cap by phase:**
  - Foundation: 600 words, 2 asks (don't overwhelm; basics first)
  - Architecture: 800 words, 3 asks (mid-revision, structural)
  - Craft: 1,000 words, 3 asks (mid-revision, sentence-level)
  - Polish: 600 words, 2 asks (final-revision, surgical)
  - Distinction: 400 words, 1 ask (publishable, optional sharpen)
- **Three-act structure** (always):
  1. *What works* (the AO Gut Reaction equivalent + 1–2 specific strengths) — builds permission to be critiqued. ~25% of word budget.
  2. *Top N edits, ranked* — each as `[location] → [what's there] → [what to do]`. ~60%.
  3. *One question to sit with* — Question Queue's top entry, only if its `would-a-17yo-act-on-it` filter passes. ~15%.
- **One voice** — admissions-reader-meets-warm-coach. Killed at the inventory-emission stage, not the render stage. (Render-stage voice fix is too late; the voice has to be baked into the finding's `observation` field.)
- **Diff-aware celebration** — if the prior round's surfaced items were actioned, the deliverable opens with "What you fixed" before "What works."

### Layer 4 — Conversation (pull-mode)

The student can ask about anything — and chat reads from Layer 1 substrate to answer. This is where the deep analysis lives that we no longer push at them.

- "What did you think of P3?" → chat queries substrate, returns paragraph-specific verdict + observations not surfaced.
- "Why didn't you mention voice?" → chat reports voice-related findings filtered out by phase.
- "Show me everything" → chat opens the substrate-level deliverable (the current 30,000-word dump as an *expandable panel*, not the default view).

Pull-mode means **the student opts into depth**. Push-mode (current) gives them depth they didn't ask for and can't process.

## 4. Per-revision flow — concrete walkthrough

Cisco's "Three Days" essay across 5 revisions. Numbers are illustrative but in the right ballpark.

### Round 1 (first analysis)

- **Layer 1:** Full pipeline runs. Generates 200+ observations into the substrate. Cost: ~$1.40.
- **Layer 2:** All 200+ observations enter inventory as `never_shown`. Each gets impact / effort / phase scoring at emission time.
- **Phase detection:** essay has scope-inflation, generic enumeration, missing community evidence → currently in **Architecture phase**.
- **Layer 3 ranker:** filters inventory to phase=Architecture, sorts by `impact / effort`, picks top 3:
  1. Cut P5 generic enumeration (impact 5, effort 2)
  2. Name a second person (impact 4, effort 1)
  3. Connect P2-P3 to milk frame (impact 4, effort 2)
- **Surface render:** 800 words, three-act structure, one voice. Each item: `[P5] → "confidence, social skills, self-worth, empathetic ability, mental fortitude" → cut three of five, replace with one specific moment of being any of them.`
- **Question:** Q1 from queue ("if you needed to witness vulnerability before being vulnerable, who started?").
- **What student sees:** the 340-word artifact from the prior audit's Section I.

### Round 2 (student returned with new draft, addressed asks 1 and 2 partially)

- **Diff detection:** P5 changed (60% rewrite). P3 added a name ("Marcus, the Detroit kid who spoke first"). P2 unchanged. P1 unchanged. P4 unchanged.
- **Layer 1 (Focused mode):** re-walk P3, P5. Re-run L3.5 for P3, P5. Re-run L4 against updated finding set. Cost: ~$0.20.
- **Layer 2 lifecycle update:**
  - Item 1 (cut P5 enumeration): targeted region changed AND issue no longer detected → `actioned` ✅
  - Item 2 (name a second person): targeted region changed AND issue resolved → `actioned` ✅
  - Item 3 (connect P2-P3 to milk frame): targeted region unchanged → `carry_forward`
- **New observations from changed regions:** L3.5 finds that the new P5 is good but the rewrite introduced a new tense slip ("I become" instead of "I have become"). L3.5 also finds Marcus addition is well-anchored but his disappearance from the rest of the essay creates a smaller version of the F14 problem.
- **Phase detection:** still Architecture, but trending toward Craft.
- **Layer 3 ranker:**
  1. Carry-forward: connect P2-P3 to milk frame (still highest impact)
  2. New: Marcus needs a callback later, OR drop the name (not as severe as F14 was, but a cleaner structural choice)
  3. New: P5 tense slip
- **Surface render:** ~250 words. Opens with "What you fixed: P5 reads completely differently — the move from 5 abstractions to one specific moment is exactly what we wanted. Marcus working too — he's anchored." Then the 3 asks. Then maybe a question if highest-impact asks have action attached.

### Round 3

- **Diff:** student added the somatic bridge to P3 ("ulcers turned to ambulance — the body kept track when I couldn't"). Didn't touch Marcus.
- **Cost:** ~$0.10.
- **Lifecycle:** carry-forward item 3 → `actioned` ✅.
- **New surface:** ~150 words. "What you fixed: the somatic bridge in P3 is the exact line — now P4's ambulance metaphor lands as completion, not surprise. Marcus is still where I'd push next. One ask, ranked higher now: …"

### Round 4

- **Diff:** student added Marcus callback, no other changes.
- **Cost:** ~$0.05.
- **Surface:** ~80 words. "I'd send this. One thing if you want it sharper: …"

### Round 5

- **Diff:** student decided not to make the optional sharpening.
- **Cost:** ~$0.05 (just confirmation).
- **Surface:** ~40 words. "This is ready. Submit it."

### Cost & deliverable trajectory across 5 rounds

| Round | Cost | Words rendered | Asks surfaced | What student feels |
|---:|---:|---:|---:|---|
| 1 | $1.40 | 800 | 3 | "I see what to do tonight" |
| 2 | $0.20 | 250 | 3 | "It's working — and there's still work" |
| 3 | $0.10 | 150 | 1 | "Almost there" |
| 4 | $0.05 | 80 | 1 | "One more thing if I want" |
| 5 | $0.05 | 40 | 0 | "Done. Submit." |
| **Total** | **$1.80** | **~1,320 words across 5 rounds** | **8 over the relationship** | |

**Compare to today's model: 5 × $1.40 = $7.00, 5 × 30,000 = 150,000 words rendered, 5 × 204 = 1,020 asks across the relationship.**

**74% cost reduction. 99% rendered-words reduction. 99% asks-surfaced reduction. Quality unambiguously goes UP because the student actually finishes the relationship.**

## 5. Dosing rules (the rules that turn architecture into product)

Independent of the architecture, these are the operational rules the system has to enforce:

### R1 — Phase-aware dose
Foundation phase: 2 asks. Polish phase: 2 asks. Architecture / Craft (the working middle): 3 asks. Distinction: 1. **Never more than 3, ever, regardless of how much analysis the system has.** The remainder lives in inventory.

### R2 — Effort-budget per round
Across the 3 asks, total estimated effort ≤ 6 (on the 1–5 scale per item). A round of feedback should not exceed ~2 hours of student work to address. If the top 3 asks would total >6 effort, drop the highest-effort one, replace with a lower-effort alternate.

### R3 — Carry-forward dampening
An ask surfaced 2 rounds in a row without action gets dropped to inventory `carry_forward + dampened`. The student has voted with their behavior. **Don't nag.** Maybe surface again after 2 rounds of silence; or wait until they ask via chat.

### R4 — Always celebrate
If the prior round's asks were addressed, the deliverable opens with explicit acknowledgment. Loss aversion is real — students who feel they're losing ground stop revising. Wins keep them coming back. **The "What you fixed" section is non-optional whenever it has content.**

### R5 — One voice, baked in
Voice unification happens at the **finding-emission** layer (L3.5 / L4 prompts), not the render layer. Each finding's `observation` field is required to be in coach-voice already. Render-stage voice repair is the wrong layer; the analytical layer must learn the voice.

### R6 — Pull-mode for depth
The Surface deliverable never contains everything. Anywhere there's a "more notes" overflow, it's an expandable / chat-accessible region. The default view is the 800-word Surface. The 30,000-word substrate is a *click* away, not a *scroll* away. Counselors and debug users find the toggle; students never click it.

### R7 — Comprehensive escape hatch
If the student says "give me everything" — chat surfaces the substrate. If they say "what about voice" — chat queries findings tagged voice. The substrate is fully exposed via pull, never via push.

## 6. Risks and mitigations

### Risk 1 — A surfaced ask is wrong, and the inventory keeps surfacing wrong asks
**Mitigation:** student feedback channel. "Helpful?" thumbs at each ask. Two negatives in a row on similar-typed asks → escalate phase detection (maybe we mis-classified the student) or tighten the impact/effort scorer.

### Risk 2 — Substrate quality drifts in Focused mode
**Mitigation:** force Comprehensive every N rounds (say 5) regardless of edits, and any time structural changes exceed threshold. Memory's `Re-analysis lifecycle` design already handles this; verify it's wired.

### Risk 3 — The student doesn't get the depth they paid for
**Mitigation:** transparent pull-mode. Chat affordance: "Show me everything you saw." If they want the 30,000-word version they get it. They almost never will, but it has to be there. Also: counselor-tier and student-tier are different deliverables on the same substrate; make sure counselors get the substrate by default, students don't.

### Risk 4 — Dosing produces a worse first impression than the dump
**Mitigation:** the first deliverable is the most important. A 340-word artifact that lands ("the milk frame is sharp; here are 3 things") is better than a 30,000-word artifact that doesn't land. Empirically test: 10 students, half see 340-word version, half see 30,000-word, measure (a) time to first action, (b) action completion rate, (c) self-reported confidence. Predicted: 340-word version wins all three by margins.

### Risk 5 — The inventory grows unbounded across many revisions
**Mitigation:** retired items prune after N rounds. Superseded items prune immediately. Inventory should remain bounded at ~50 active items per essay. Beyond that, the student is in revision-spiral and a different intervention is needed (probably a chat conversation, not more inventory).

### Risk 6 — Phase detection mis-classifies and the wrong asks get surfaced
**Mitigation:** phase is recomputed every round, not sticky. Memory's `Progressive Precision` design specifies this. If round-2 surfacing feels off, the student can chat: "I think I'm in Polish, not Architecture" — and the system can override.

### Risk 7 — Cost goes up, not down, because Focused mode is more expensive than expected
**Mitigation:** instrument cost telemetry per round. If Focused mode > 30% of Comprehensive cost, the design isn't working. Memory's acceleration target is Round 5 = $0.03; if we land at $0.30 we have a problem.

## 7. What this looks like in code (sketch)

### The render contract

```typescript
type SurfaceDeliverable = {
  whatWorks: {
    aoGutReaction: string;          // 2-3 sentences, AO voice
    preservedStrengths: string[];   // 1-2 strengths, "don't touch this"
  };
  
  whatYouFixed: ActionedAck[];      // ONLY when prior asks were addressed
  
  asks: Array<{
    rank: 1 | 2 | 3;
    location: ParagraphRef;
    whatsThere: string;             // the problem, in coach voice
    whatToDo: string;               // the action, in coach voice
    expectedImpact: string;         // why it matters
  }>;
  
  questionToSitWith?: string;       // optional, only if it passes the 17yo filter
  
  meta: {
    phase: ImprovementPhase;
    round: number;
    wordCount: number;              // hard cap by phase
    askCount: number;               // hard cap by phase
  };
};
```

### The render function

```typescript
function renderSurface(
  inventory: InventoryItem[],
  priorRound: SurfaceDeliverable | null,
  diff: EssayDiff,
  phase: ImprovementPhase,
): SurfaceDeliverable {
  const dose = doseRules[phase];                        // R1
  
  const actioned = priorRound 
    ? detectActioned(priorRound.asks, diff, inventory)  // R4
    : [];
  
  const candidates = inventory
    .filter(i => i.phase === phase || i.phase < phase)  // R1 (current and earlier phases)
    .filter(i => i.status !== 'actioned' 
              && i.status !== 'retired' 
              && i.status !== 'superseded')
    .map(scoreImpactPerEffort)
    .sort(byScore);
  
  const picked = pickWithEffortBudget(candidates, dose);  // R2
  
  return {
    whatWorks: composeWhatWorks(inventory, dose.maxStrengths),
    whatYouFixed: actioned.map(toAck),
    asks: picked.map((item, i) => toAsk(item, i + 1)),
    questionToSitWith: pickQuestion(inventory, dose),
    meta: { phase, round, wordCount: countWords(...), askCount: picked.length },
  };
}
```

### The diff handler

```typescript
function updateInventoryFromDiff(
  inventory: InventoryItem[],
  newSubstrate: Substrate,
  diff: EssayDiff,
): InventoryItem[] {
  return inventory.map(item => {
    if (regionDeleted(item.location, diff)) return { ...item, status: 'retired' };
    if (!regionTouched(item.location, diff)) return item;
    
    const stillDetectable = checkAgainstSubstrate(item, newSubstrate);
    if (!stillDetectable) return { ...item, status: 'actioned', actionedRound: diff.round };
    return { ...item, status: 'carry_forward' };
  });
}
```

These are sketches; the real implementations have to integrate with `FindingStore`, `selectAnalysisMode()`, and the existing pipeline.

## 8. Concrete next steps (ranked)

### Step 1 — Fix the existing dump renderer to match phase (1 day, no new code)
The `ImprovementPhase` field is *already in `ProfileIndex`* per memory. Today the renderer ignores it. Make the renderer filter by phase: don't show Craft-phase observations to a Foundation-phase student. **This alone should compress the visible dump by 40–60%** without any architectural change. Lowest-risk highest-leverage move.

### Step 2 — Build the Surface deliverable as a separate render layer (~1 week)
Don't replace the existing dump. Add a new `renderSurface()` that produces the 340-word three-act artifact. The dump stays for counselors / debug; the Surface becomes the student-facing default. Existing `FindingStore` + `ImprovementPhase` provide everything needed.

### Step 3 — Voice unification at finding-emission (~1 week)
Update L3.5 + L4 prompts to require findings be written in admissions-coach voice (concrete examples in the prompt). Key constraints to add:
- No schema labels in the observation field (`[emotional_setup]`, `confidence: 0.5`, etc.).
- No paragraph IDs of form `P3S4` — use "your third paragraph, the ambulance line."
- No academic-craft jargon ("triadic structure," "tonal disposition," "structural irony"); plain language only.
- No celebratory tone ("sophisticated," "genius," "architecturally interesting"); admiring is fine, fan-voice is not.

### Step 4 — Inventory lifecycle wiring (~1–2 weeks)
Extend `FindingStore` with the lifecycle states (`surfaced / actioned / carry_forward / superseded / retired / never_shown`) and the diff-driven status updater. Memory says this is partially built (`Step 9 — re-analysis context + FindingStore threading`). Audit what's there before re-implementing.

### Step 5 — "What you fixed" celebration loop (~3 days)
Once lifecycle is wired, the celebration is just a render-time addition. Detect `actioned` items since prior round, render acknowledgment block. Easy.

### Step 6 — Empirical validation (~1 week, ongoing)
A/B test the 340-word Surface vs the 30,000-word dump on real students. Measure (a) time to first action after receiving feedback, (b) action completion rate, (c) self-reported confidence, (d) revision-cycle continuation rate. **No architectural commitment beyond Step 1 should ship without this data.**

### Step 7 — Pull-mode chat affordance (~1 week)
"Show me everything," "what about voice," "why didn't you mention X" — these are chat queries against the substrate. The substrate is already addressable per `essayIntelligence` profile router. Wire chat to it; surface the affordance in UI.

## 9. The one-line summary

**Today the system pays $1.40 every round to regenerate the same 200 observations and dump them at the student. The student reads 5%. We are paying for analysis no one consumes.**

**The product the system should ship is a paced coaching relationship: comprehensive intelligence in the substrate, scarce intelligence at the surface, persistent inventory across rounds, dosed by phase, with celebration when work lands.** Five rounds of revision should cost <$2 total, render <1,500 words total, and surface ~8 asks across the entire relationship — not 1,020.

**Cost goes down as a *consequence* of the design, not the goal.** The goal is a deliverable a student finishes, understands, and acts on. Cost reduction follows automatically because we stop paying for output the student would never see.
